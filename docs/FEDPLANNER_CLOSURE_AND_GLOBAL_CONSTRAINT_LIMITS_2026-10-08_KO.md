# Closure의 임시 Clause와 MRV 이후 공동 제약은 무엇인가

2026-10-08 현재 구현을 기준으로 설명한다. 아래 숫자와 프로그램은 개념 설명용이며 실행 측정값이 아니다.

앞의 두 문장은 서로 다른 한계를 말한다. **첫째는 압축하는 시점의 문제이고, 둘째는 합법성을 증명한 범위의 문제다.**

| 앞서 한 설명 | 정확한 의미 |
|---|---|
| Closure 내부의 임시 Clause 생성이 남아 있다 | 일부 경로는 조합마다 객체를 만든 후 최종 공개 단계에서 ID로 바꾼다. 최종 저장량은 줄지만 앞선 객체 생성·병합 비용까지 없어지지는 않는다. |
| MRV가 모든 전역 제약을 해결하지는 못한다 | MRV는 다음에 선택할 입력의 순서를 정한다. 연결된 제약으로 가지를 줄일 수 있지만, 다른 연산·분기·함수 호출의 선택까지 자동으로 증명하지는 않는다. |

“공유 비용”을 합법성 검사와 함께 묶었던 표현은 부정확했다. 공동 제약은 **함께 선택해도 되는가**, 공유 비용은 **함께 선택했을 때 얼마인가**의 문제다.

**1. Closure와 Clause가 각각 하는 일**

Closure는 앞뒤 연산의 후보와 의존 관계를 전파하면서, 더 이상 바뀌는 것이 없을 때까지 분석을 갱신하는 과정이다. 실제 데이터를 worker에서 계산하는 실행 단계가 아니다.

Support clause 하나는 특정 출력 후보를 만들기 위한 **입력 선택 한 묶음과 그 근거**다. 예를 들어 `z = x + y`의 어떤 출력 후보를 만들 때 다음 정보를 묶는다.

```text
입력 0: x의 source 후보 X2를 특정 relocation으로 공급
입력 1: y의 source 후보 Y5를 DIRECT로 공급
근거: 필요한 relocation proof, worker 배치 관련 증거 등
```

Clause가 무겁다는 말은 행렬 데이터를 복사한다는 뜻이 아니다. 이런 묶음마다 객체·입력 목록·proof 목록을 만들고, 정규화·비교·중복 제거·병합하는 비용이 누적된다는 뜻이다. 이전 연산의 모든 실행 이력을 매번 깊게 복사한다는 의미도 아니다.

현재 일부 경로는 다음과 같이 처리한다.

```text
입력별 후보
  → privacy 필터, source 일관성 검사, MRV·부분 oracle pruning
  → 살아남은 조합의 binding/proof를 담은 realization·clause 생성
  → Closure에서 후보 관계 전파·병합
  → 관계가 확정되면 publication
  → 공유 사전 + 합법 조합 ID 형태로 보관
```

이 흐름은 여러 단계의 역할을 요약한 것이다. 모든 검사가 하나의 함수에서 순서대로 실행된다는 뜻은 아니다. 또한 독립적인 입력 product를 처음부터 factorized 형태로 만드는 경로도 이미 있으므로, **모든 조합이 반드시 명시적 clause를 거치는 것은 아니다.**

**2. 마지막에 ID로 바꾸는 것만으로 생성 비용이 없어지지 않는 이유**

가령 어떤 경로가 분석 도중 clause 1,000개를 만들었고, 병합 결과 최종 관계에는 800개 조합이 남았다고 하자.

```text
현재 남아 있는 경로: clause 생성·병합 → 최종 800개를 사전과 ID로 표현
추가 개선 방향:     조합 발견 시 사전을 참조하는 ID를 추가·병합
```

첫 번째 방식도 최종 저장량과 이후 객체 중복을 줄인다. 하지만 이미 수행한 1,000개 clause의 생성·처리 비용을 되돌릴 수는 없다. ID로 변환하는 작업에도 비용은 든다.

여기서 “임시”는 최종 공개 이전의 구성 과정에서 사용하는 객체라는 뜻이다. 모든 객체가 즉시 버려진다거나, Closure가 반복할 때마다 전체 product를 처음부터 다시 만든다는 뜻은 아니다. 기존 중복 제거·증분 처리의 효과와 별개로, 살아남은 조합을 명시적 객체로 만드는 경로가 남아 있다는 설명이다.

앞선 테스트의 “완전히 materialize한 clause 저장 수 0”도 **변환된 relation이 원래 clause 목록을 보관하지 않는다**는 의미다. 분석 시작부터 객체를 한 번도 만들지 않았다거나, downstream의 handle·상태까지 0개라는 뜻은 아니다.

따라서 시간을 대략 다음처럼 나누어 봐야 한다.

```text
전체 시간 = 후보 탐색·검사 + Closure 객체 구성·병합
          + ID 변환 + downstream 모델 구성·비용 계산·선택
```

MRV는 주로 탐색하는 가지를 줄인다. ID 저장은 관계의 표현을 줄인다. 둘 다 적용해도 Closure의 모든 객체 구성 비용과 downstream 계산까지 자동으로 없어지지는 않는다.

**3. 합법 ID인데도 남는 검사가 있다는 말의 정확한 범위**

현재 ID는 **특정 realization의 support relation 안에서 이미 받아들인 전체 입력 조합**을 가리킨다. 프로그램 전체의 모든 연산 선택을 확정한 실행 계획에 붙인 인증 번호는 아니다. 번호의 의미도 해당 relation과 사전에 속한다.

따라서 두 경우를 구분해야 한다.

| 상황 | 처리 원칙 |
|---|---|
| 같은 relation·사전·판정 문맥에서 이미 합법으로 저장한 조합을 읽음 | 그 조합을 받아들일 때 증명한 동일 조건을 oracle에 다시 물을 필요가 없다. |
| 서로 다른 연산의 합법 ID들을 함께 선택함 | 각 ID가 요구하는 producer·값 버전·호출 문맥 등이 서로 맞는지 확인할 수 있어야 한다. |

예를 들어 consumer 후보의 ID가 “producer P의 물리 결과 P1을 사용한다”고 기록했는데, 전체 계획에서는 P2만 만들기로 했다면 두 선택은 맞지 않는다. Consumer ID 자체가 불법이었던 것은 아니다. **P1을 공급한다는 전제에서 합법인 후보와, 그 전제를 충족하지 않는 다른 선택을 결합한 것**이다.

한 입력 묶음 안에서 같은 source owner의 선택이 충돌하는 경우는 현재 생성 단계에서 일찍 제거한다. 그 검사를 했다는 사실만으로 다른 연산의 최종 선택까지 모두 일치한다고 결론 내릴 수는 없다.

공동 조건까지 이미 포함해 검증한 ID relation이라면 그 조건도 그대로 재사용하면 된다. 남겨야 하는 것은 아직 그 증명에 포함되지 않은 관계다. **“합법 ID를 저장해도 모든 검사를 처음부터 반복해야 한다”는 설명이 아니다.**

**4. VALUE_MAP과 joint 조건: 같은 worker·ROW여도 값의 출처는 다르다**

다음 프로그램에서 A, B, C, D는 같은 크기이고, 모두 같은 전체 worker 집합에 ROW로 배치되어 있다고 가정하자.

```text
if cond:
    x = A
    y = B
else:
    x = C
    y = D
z = x + y
```

배치만 보면 네 값이 모두 같은 종류다. 하지만 실행 중 `z`에 함께 도달하는 값은 다음 두 묶음이다.

| 함께 도달하는 값 | 프로그램상 가능 여부 |
|---|---|
| x=A, y=B | cond가 참이면 가능 |
| x=C, y=D | cond가 거짓이면 가능 |
| x=A, y=D | 이 프로그램에서는 함께 도달하지 않음 |
| x=C, y=B | 이 프로그램에서는 함께 도달하지 않음 |

VALUE_MAP 관련 분석은 이런 경계에서 읽는 값이 어느 정의·물리 결과로 연결되는지를 다룬다. Joint 관계는 여러 입력의 출처가 **함께 어떻게 연결되는지**를 보존한다. 개별 입력의 가능한 출처만 모아 product를 만들면 이런 상관관계가 사라질 수 있다.

이 예시는 공동 관계의 필요성을 설명한다. 현재 Closure가 위 네 묶음을 항상 생성한다는 실행 추적 결과는 아니다. 실제 계획은 도달 가능한 두 분기의 요구를 보존해야 하며, planner가 더 싼 분기만 골라 실행한다는 뜻도 아니다.

따라서 “모든 worker를 사용한다”는 가정으로 이 구분이 없어지지는 않는다. Worker 수나 배치가 같아도 **어떤 값이 어느 경로에서 만들어졌는가**는 다를 수 있다.

**5. 함수 경계: 같은 함수여도 호출별 연결을 보존해야 한다**

```text
u = f(A)
v = f(B)
z = u + v
```

`f`의 형식 인자 이름이 같다는 이유로 두 호출의 입력과 반환값을 섞을 수는 없다. `u`는 A를 넘긴 호출의 결과, `v`는 B를 넘긴 호출의 결과로 연결되어야 한다. 각 호출의 입력·출력 배치와 privacy 조건도 연결된 문맥에서 유효해야 한다.

UDF에 일반 연산 kernel의 부분 oracle를 적용하는 것이 무의미해 그 검사를 건너뛰더라도, 이러한 호출 연결의 의미까지 없어지지는 않는다. 현재 FunctionCall의 완전 판정은 경계 연결에 필요한 placeholder 의미도 가지므로 무조건 제거하지 않았다.

**6. 공유 비용: 합법 여부만으로 가격이 정해지지 않는 경우**

같은 값·버전의 업로드를 두 연산이 재사용할 수 있다고 하자. 동일한 공급이며 필요한 수명 동안 재사용할 수 있음이 확인된 상황이다.

```text
업로드 비용 = 10
연산 C1 비용 = 2
연산 C2 비용 = 3

각 연산에 업로드를 따로 더함: (10 + 2) + (10 + 3) = 25
공유 업로드를 한 번 계산함:   10 + 2 + 3 = 15
```

합법 ID로 각 선택을 표현할 수는 있다. 그러나 총비용을 정확히 계산하려면 어느 선택들이 같은 업로드를 요구하는지 알아야 한다. 다른 값·전송·수명을 같은 업로드로 취급해서도 안 된다.

이것은 oracle 합법성 재검사가 아니라 **선택된 조합의 비용을 중복 없이 계산하는 일**이다. 입력별 비용을 무조건 더하거나, 공유 효과를 무시하고 로컬 비용이 큰 후보를 버리면 최적 계획을 잃을 수 있다.

**7. MRV로 할 수 있는 일과 앞으로 옮길 수 있는 일**

MRV는 현재 선택으로 축소된 domain을 보고, 가능한 후보가 가장 적은 입력부터 선택한다. Forward checking은 선택 직후 나머지 입력에서 불가능해진 후보를 제거한다. 두 기능이 강해지려면 해당 시점에 사용할 정확한 제약이 있어야 한다.

현재 source 일관성·일부 operation의 부분 oracle를 연결했다. MRV 자체가 모든 VALUE_MAP·함수·공유 비용 관계를 새로 알아내는 것은 아니다. Downstream의 joint factor에도 부분 판정이 있으므로, 모든 공동 검사가 완전한 계획을 만든 뒤에만 실행되는 것은 아니다.

남은 개선 방향은 다음처럼 나뉜다. 이번 문서 작성에서 새로 구현한 내용은 아니다.

| 대상 | 추가 개선 방향 | 지켜야 할 조건 |
|---|---|---|
| Closure 객체 구성 | 처음부터 공유 사전과 ID로 추가·중복 제거·증분 병합 | 갱신되는 source/proof와 ID 사전의 대응을 정확히 유지 |
| 공동 합법성 | 정보가 확보된 제약을 생성 단계의 부분 검사 또는 검증된 ID 관계로 이동 | 아직 모르는 상태를 불법으로 취급하지 않음 |
| 공유 비용 | 선택 ID들이 요구하는 공통 공급을 별도 비용 관계로 계산 | 실제로 공유 가능한 경우만 한 번 계산 |

사용자가 제안한 “합법인 조합의 인덱스만 기억하자”는 방식은 공동 관계에도 적용할 수 있다. 다만 프로그램 전체의 모든 합법 조합을 먼저 나열해 ID로 저장하면, 원래 downstream에서 하던 조합 탐색을 앞단으로 옮겨 다시 폭발시킬 수 있다. 필요한 범위별로 검증된 관계를 보관하고 연결해야 한다.
