## 실행 및 frozen-engine 증거

- 최종 Memo 회귀 실행은 775개 테스트가 통과했고, origin canonicalization과 shared runtime을 포함한 최신 targeted 실행도 통과했다. 보존 로그는 `final-memo-regression-test-output.txt`와 `final-origin-tests.txt`이다.
- propagation과 projection 수정 과정의 이전 실패 로그는 최종 성공 증거로 사용하지 않는다. 특히 `projected-regression-test-output.txt`의 269개 중 1개 실패는 이후 수정 전 실행이다.
- `provenance-validation.json`은 `engine-v8-sha256.json`의 8,903개 frozen 파일을 모두 다시 해시했고 누락·추가·불일치가 0임을 기록한다. manifest의 Java source 3,981개도 현재 workspace와 모두 일치한다.
- 동일 provenance 기록은 baseline `memo-dual-improvement-20261015/engine-v3`의 8,881개 frozen 파일을 모두 검증하고, manifest source 3,975개를 비교 기준 commit `5734de2021f2841d82539063a6b450db69b9f7cb`과 대조해 누락·불일치가 0임을 확인한다.
- 최종 엔진에만 있는 Java 파일은 `MemoLocalOptimizer`, `MemoLocalMessages`와 대응하는 네 test class를 포함한 6개이며 baseline에 없는 것이 예상된 상태로 기록된다.

남은 핵심 한계는 model이 같은 `Hop`·같은 statement block의 여러 occurrence는 canonicalize하지만, 서로 다른 HOP이 Lop 생성 중 하나의 물리 producer로 합쳐지는 경우를 unit fixture에서 직접 증명하지 못했다는 점이다. lowering은 이 경우를 계속 fail-closed로 검사하며 충돌 시 모든 `DefinitionSite`를 출력한다. 최종 Docker LogReg fullcompile은 관측됐던 충돌의 회귀 검증이다. 대규모 LogReg 전체 학습의 runtime 검증은 아니며, 수치 실행 검증은 별도의 작은 linear/logistic 및 shared-function fixture에 한정한다.

`LocalStatistics.messageTouchedVariables`, `messageTouchedFactors`, `completedMessages`, `untouchedBuckets`는 **message kernel이 처리한 작업만** 센다. 초기 UB seed 생성, 전체 witness validation, search 중 비용·합법성 평가가 접근한 factor까지 포함하는 총계가 아니다. 따라서 이 counter가 작다는 사실만으로 전체 optimizer가 같은 수의 factor만 읽었다고 해석하면 안 된다.

최종 Docker `evaluation/` 감사는 195/195 compile 시도, 119 certificate, 4,515개 LB/UB 지점을 검증했다. 49개 새 Local 결과 모두 root direct exact 시도/해결 0이고 정책·action 순서·terminal counter 검사를 통과했다. 별도 Docker JUnit 18개(실제 worker를 사용하는 method 11개와 compiler/binding method 7개)와 synthetic 42개 row도 통과했다. 이 증거는 위 표의 더 강한 fault-injection/selector/large-runtime 조건을 자동으로 Covered로 바꾸지 않는다. 성능 회귀와 실험 범위는 기술 보고서 §5에 기록했다.
